# One executor, one independent QA, final human

## Applicability and actual dispatch

Document-level translation/build/substantial repair uses exactly the main agent (executor + coordinator) and one ordinary independent QA. No extra scheduler or recursive dispatch. Reuse that QA thread for subsequent batches and repair checks. Excerpts, Q&A and tiny deterministic edits need only proportional self-check. Use `gpt-6.2-sol/high` for translation and forward acceptance runs. Dispatch independent QA explicitly as `gpt-6.2-sol/medium` with a fresh context and only the relevant source, current target and scope. Record effective model and effort from the runtime when available. After medium inspection, a genuinely unresolved qualifier, formula relationship, dense diagram or conflicting extraction/render evidence can warrant high for that specific object. Record the reason, IDs and changed effort. Ordinary length, page count and routine checks use medium. Where the current QA cannot change effort, let the high executor resolve the issue against source and return evidence to the same medium QA; report the actual settings. A role is not an assessor qualification.

Current Codex supports standalone personal `~/.codex/agents/*.toml` and project `.codex/agents/*.toml` with `name`, `description`, `developer_instructions`. Project `[agents].max_concurrent_threads_per_session=1` caps spawned agents, excluding main. The project configuration template supplies the Sol 6.2 default. The QA role pins Sol 6.2 and medium reasoning independently of the parent. Do not edit system/plugin-managed files or weaken platform restrictions. Existing desktop turns may expose a direct spawn tool without a custom-role selector: use one real child with the same role instructions, fresh context (`fork_turns=none` where supported), and record the tool-returned ID. Installing a TOML file alone is not proof of dispatch. Record the actual channel/tool used and limitations; unavailable capability is not independent QA PASS.

## Handoff protocol

1. Executor finishes a stable batch/snapshot: exact source/candidate/input paths and hashes, approved terms/decisions/profile, source page scope, known renderer and QA evidence output directory. Use `workflow.py snapshot --spec ... --output ...`. It hashes only named current dependencies, refuses changed inputs and refuses overwrites.
2. Send QA raw English source and candidate, applicable approvals and scope, NOT executor findings/PASS or a list of suspected defects. QA independently inventories the source page-by-page, including images/streams/footnotes not present in extraction. On a full job, don't limit QA to executor-listed objects. Pilot scopes can be small but must be labeled partial.
3. Use file-based command-line render, extraction, font and link checks throughout. Never use Computer Use, desktop/browser controls or the clipboard. QA returns one batch of independent findings and coverage, then may compare executor's ledger/reports for reconciliation. Each conclusion names evidence and limitations. Stable input hash is rechecked before accepting the report. Only QA evidence directory is writable to QA; this is a role constraint, not a claim of OS isolation. QA never operates Word, alters production, closes human decisions or lowers thresholds.
4. Executor routes with `workflow.py route`: pending work separately; clear-source same-goal fixes to auto-repair backlog; uncertain technical meaning/source editorial change/approved-term change/external permission to grouped human handoff. Apply versioned preconditioned repairs to a new candidate. QA repeats affected scope/dependencies, not unrelated complete work.
5. Two rounds with the same failure fingerprint and unchanged evidence/repair result trigger `ROOT_CAUSE_DIAGNOSIS_REQUIRED`. Inspect the checker or root cause before another build. Independent work continues; don't repeatedly ask for identical routine repair approval.
6. Final source coverage and all applicable actual pages must be accounted for. Executor prepares exact final artifacts and coordinates the stability check for the actual production pipeline: independent dual Word exports for DOCX/Word-authoritative work; the direct PDF path in pdf_workflow.md otherwise. Only executor controls Word when that route needs it. Plain-text tasks do not need page rendering. QA checks the actual outputs and source fidelity. Human confirms the artifact-bound final proofreading; formal publication is a separate authorized state.

## Prompt to the one QA

For paginated translations, establish the source's layout before viewing the candidate. Compare corresponding rendered regions by object even if page numbers move. In the existing review, identify source and target locations and the observed layout (e.g. column order and spans, margin marks, note anchors and bodies, figure groups and label language where present). Independently compare main-text baselines across same-style paragraphs and visible gaps at paragraph, figure and table boundaries in the candidate. Check both columns above spanning objects and inspect intentional float or footnote space in context. Record readability and source layout separately. Resolve any material unrequested change before first delivery, or report the exact unverified or technically blocked scope.

“You are the independent QA, not a production editor. Read the snapshot and approved source/profile first. Independently inventory every source content layer in the declared scope and inspect the candidate, including actual visual pages; do not assume the executor inventory is complete. Do not read executor PASS/findings before your first independent report. Write only QA evidence to the specified directory. Return one batch of findings with source/target locator, evidence, severity, recommended disposition and checked/total coverage. Identify omissions and checker blind spots. Do not call Word, edit production, spawn agents, switch models, or decide source corrections. Same wording repeated at separate true anchors is not automatically duplication. State coverage limits honestly.”
